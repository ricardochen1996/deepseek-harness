# Agent Note: 允许 profile 在多个 Session 之间共享同一个附加浏览器

Status: proposed

[English](2026-10-18-attach-browser-sharing-between-sessions.md) | 中文

## 问题

浏览器操作契约把附加浏览器的归属写成了一条绝对句：「附加的浏览器仍归外部所有。提供方在该提供方实例内将浏览器保留给一个 Session，保留现有浏览器状态，并拒绝另一个 Session 同时附加」（[浏览器操作](../../../../docs/subsystems/browser-use.zh.md)）。拥有这句话的决策是[浏览器操作提供方注册](../../implemented/architecture/2026-09-12-browser-use-provider-registration.zh.md)，它把同一件事作为所描述运行时的一个属性重复了一遍。

这个默认是对的：两个 Session 驱动同一个外部浏览器会争它的标签页和登录态，而一个不声明就同时接纳两者的提供方，会把这种冲突变成看不见的故障。问题在于契约到此为止。它没有第二句话，于是提供方无法让一个 profile 明知后果地选择相反的取舍——可这种情况很平常：一个人、一个已登录的 Chrome、几个对话。最先用到浏览器的那个 Session 会一直持有整份保留（直到它关掉那个浏览器或被释放），一个闲置的对话能挡住浏览器几个小时；而被认可的出路只有等待，或者自己起一个浏览器——后者恰好丢掉了当初选择附加所要的登录态。

少一句话并没有阻止提供方把它做出来。至少有一个仓外提供方已经提供显式开关（`@ricardochen1996/dsh-browser-use` 的 `attachSharing: shared`），于是附加行为实际上已按提供方各自决定，而契约读起来仍是一条禁令。这正是本提案要解决的漂移：要么"拒绝第二个 Session"是契约的要求，要么它只是一个 profile 可以放弃的默认值——而答案应该写在提供方作者会读的地方。

## 提案

保留独占附加作为契约的默认值，并在它旁边写出这个有意的放弃开关。在[浏览器操作](../../../../docs/subsystems/browser-use.zh.md)的「Session 所有权」一节里，关于附加浏览器的那一段在保留之后增加一句，英文文档增加它的对应句：

> 本次激活可以为自己的提供方实例显式放弃该保留，此时该实例内每个 live Session 都可以同时驱动这个附加浏览器。共享必须让每个 Session 的连接与标签页各归其主：一个 Session 只关自己打开的那个标签页，清理过程中绝不关闭这个外部浏览器。

拥有这条保留的决策记录——[浏览器操作提供方注册](../../implemented/architecture/2026-09-12-browser-use-provider-registration.zh.md)——必须在同一变更里同步更新，让两者永不互相矛盾，这是 [implemented/AGENTS.md](../../implemented/AGENTS.md) 的要求。

有两件事契约应当刻意不说。它不应点名配置项：配置键属于提供方自己的界面，写进契约等于冻结某个提供方的 YAML。它也不应描述实现机制：连接复用、按 daemon 分配标签页、保留的记账方式都是提供方的内部机制，而这份契约会被多个提供方的作者读到。

### 共享必须保证什么

只有在下列不变式之下，共享附加才是可接受的；上面那句话把前两条变成规范性的要求：

- **每个 Session 一个标签页。** 每个 Session 经由自己的连接驱动自己的标签页；它不导航、不接管、也不关闭别的 Session 的标签页。
- **清理只作用于本地。** 关闭某个 Session 的浏览器只关它自己的标签页并断开连接。它绝不终止或导航其他 Session 仍在使用的那个外部浏览器。
- **共享状态是有意的。** Cookie、存储与登录身份都属于那个外部浏览器，所以共享意味着两个对话以同一个人的身份行动。这正是附加的用途，也是这个选择属于 profile 而非提供方默认值的原因。
- **后来者不能驱逐。** 附加到一个已被共享的浏览器时，该 Session 只取自己的标签页；它不释放、不改派、也不让别的 Session 的持有过期。
- **默认仍是独占。** 什么都不写的激活，行为与今天完全一致。

有一项已知交互属于实现该能力的提供方自己的文档，而不是契约：类 browser-harness 的引擎可能在某个 Session 第一次打开页面时顺手清掉没人用的**空白**标签页，这可能关掉另一个 Session 还没用过的标签页。它只限于空白页，受影响的 Session 下次调用会重开一个标签页，但提供共享的提供方应当写明这一点。

## 考虑过的替代方案

- **维持绝对禁令。** 第二个对话改为自己起一个浏览器。否决：自起的浏览器没有用户的任何登录态，而那正是选择附加的全部理由，于是常见场景只有在重新登录之后才被服务。
- **把共享作为契约默认值。** 否决：它会静默改变每个既有附加激活的行为，而独占的理由——标签页与登录态——对默认值依然成立。一个多数时候正确的默认值，不该为了服务反正会主动放弃它的场景而翻转。
- **让共享服务来仲裁。** 由 `ctx.browserUse` 发放一个可多方持有的租约。暂时否决：该服务拥有的是一个提供方槽位，不是浏览器资源；而"谁可以附加"今天已经由共享运行时拥有的激活动员规则决定。在那里加租约比改一句契约大得多，而且并非阻止漂移所必需。
- **只在提供方自己的文档里决定。** 否决：契约里那句话是规范性的、读起来就是禁令，照着它做的提供方作者不会提供这个开关，而下一位评审者会把仓外行为当成缺陷。
- **什么都不记，留着漂移。** 否决：那样两个提供方会对"第二个 Session 能否附加"给出不同答案，而没有任何记录说明当初想要哪个答案。

## 验收标准

- [浏览器操作](../../../../docs/subsystems/browser-use.zh.md)与其英文对应文以同样的措辞把保留写成带显式放弃开关的默认值，并且拥有这条保留的决策记录在同一变更里被更新或取代。
- 没有任何规范性句子禁止提供方提供该开关，也没有任何句子要求特定的配置键名或实现方式。
- 上述不变式写在提供方作者会读的地方，且默认行为不变：同一个附加浏览器上的两个 live Session，第二个仍被拒绝。
- 提供共享的提供方应能被观察到地验证：两个 live Session 同时驱动一个附加浏览器、各自在自己的标签页里；关闭其中一个 Session 的浏览器后，另一个的标签页与那个外部浏览器都还在；而要求默认行为的 profile 仍然拒绝第二个 Session。
- 文档门禁通过：该记录位于 `proposed/architecture/` 且为 `Status: proposed`，中英两侧保持配对，`pnpm run verify-agent-note-format` 与 doc-sync 门禁一致。

## 风险

- **身份混用。** 共享让两个对话更容易以同一个已登录身份行动。缓解在于它是显式开关、且是这个 profile 自己选择了附加；契约不得把共享描述成无害。
- **跨 Session 干扰。** 提供方的缺陷会变成用户可见的「另一个对话关掉了我的标签页」。这些不变式的好坏取决于实现它们的提供方，这也是它们被写成规范性要求而非描述的原因。
- **同一个浏览器内部的竞态。** 一个浏览器支持多个 CDP 客户端，但同站存储与 service worker 是共享的；提供方不得承诺引擎给不出的隔离。
- **把许可读成默认。** 后来的作者可能把"可以被共享"读成"应该被共享"。措辞必须把默认那句放在前面，并明确写清放弃开关是 profile 的选择。
- **判断错误的代价。** 如果共享被证明有害，默认值未被动过：回退是某个 profile 改回一个设置，而不是一次契约变更。
